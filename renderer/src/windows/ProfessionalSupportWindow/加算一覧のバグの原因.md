今回の「専門的支援加算一覧の取得漏れ」の原因は、Electron側の一覧取得処理で、HUGへ検索条件をPOSTした際のレスポンスを「必ず1ページ目」として扱っていたことです。

HUG側では対象月の専門的支援実施加算が153件存在していましたが、Electron側で実際に取得できていたのは129件でした。つまり、DB保存後にデータが消えたのではなく、HUGの一覧をElectronで取得する段階ですでに24件不足していました。

従来の処理では、検索条件をPOSTしたレスポンスから最初の一覧データを取得し、それを1ページ目のデータとして扱ったあと、2ページ目以降を `?page=2`、`?page=3` のようにGETしていました。しかし、HUGの `record_proceedings.php` は検索条件や現在表示しているページ位置をセッション側で保持している可能性があり、検索POSTのレスポンスが必ずしも1ページ目になるとは限りません。そのため、例えばPOSTレスポンスとして6ページ目が返った場合でも、それを1ページ目として扱ってしまい、その後は2ページ目以降だけを取得するため、本来の1ページ目を一度も取得しない状態になる可能性がありました。

また、POSTレスポンスのページと、その後GETで取得したページが重複する場合もあります。その結果、重複排除後の実取得件数がHUG側の本来の件数より少なくなり、今回のケースでは153件あるはずの一覧が129件まで減っていました。

さらに、取得漏れを見つけにくくしていた原因として、取得結果の件数を返す際に `Math.min(total, uniqueRecords.length)` を使用していた点があります。本来HUG側が153件と返していても、Electron側で129件しか取得できていない場合、この処理によって `total` まで129件に書き換えられていました。そのため、本来は「HUG側153件・実取得129件」という異常な状態であるにもかかわらず、画面上や後続処理では「total 129件・取得129件」と見え、正常に全件取得できたように見えていました。

今回の不具合の流れをまとめると、検索条件をPOSTする → POSTレスポンスを1ページ目だと誤認する → 2ページ目以降だけをGETする → 本来の1ページ目など一部ページが取得されない → 重複を削除すると153件から129件になる → `Math.min()` によって本来の153件という情報まで129件に書き換わる → 129件のままLaravelへ送信されDBへ保存される、という状態でした。

そのため、今回の直接的な原因はLaravelやDBの保存処理、`GetProfessionalSupportMonth` の集計処理ではなく、Electron側のHUG一覧取得時のページング処理にあります。

修正版では、検索POSTは検索条件をHUG側へ設定するためだけに使用し、そのPOSTレスポンス自体を1ページ目として利用しません。検索後に `page=1` から最終ページまでをすべて明示的にGETすることで、現在のページ位置に依存せず全ページを確実に取得するようにしています。

また、HUG画面に表示されている総件数と、Electron側で実際に取得できた件数を別々に保持し、両者が一致しない場合はエラーとして保存処理を中断するようにしています。これにより、今後同様のページング仕様変更や取得失敗が発生した場合でも、データが不足した状態のままDBへ保存されることを防げるようになります。
