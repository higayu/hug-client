# ConfigTab 保存ボタンの処理調査

調査日: 2026-11-08

## 概要

「ID・パスワードの変更を保存」ボタンは、フォームの14項目を整形して `config.json` に保存し、成功後に Redux とフォームを更新して、Laravel API からデータを再取得する。

本資料はソースコードを静的に確認した結果。実際の保存・API通信は実行していない。アプリケーションのコード変更は行っていない。

## 1. ボタンと入力状態

- `index.jsx:477` のボタンは `type="button"` で、クリック時に `handleSave`（同ファイル106行目）を呼ぶ。
- `isSaving` が `true` の間はボタンを無効化し、表示を「保存中...」にする。
- フォームの初期値は `createConfigFormState(appState)`。対象の appState の値が変わると `useEffect` でフォームも作り直す。
- 通常入力は `handleInputChange` でフォームだけを更新し、ロックのチェックボックスは真偽値をフォームに設定する。

## 2. クリック後の処理順序

1. **保存中か確認**: `isSaving` が `true` なら処理を終了。それ以外は `setIsSaving(true)`。
2. **入力値を整形**: `normalizeConfigData(form)` で保存用の14項目を生成する。
3. **ロックの入力チェック**: ロックが有効でパスコードが空の場合、「ロックをONにする場合はパスコードを入力してください」という例外を発生させる。この場合はファイル保存しない。
4. **ファイルを保存**: 整形済みデータをコンソール出力し、`await saveConfig(configData)` を実行する。
5. **保存結果を確認**: 戻り値が `false`、`null`、`undefined`、または `success === false` の場合は例外にする。現在の `saveConfig` は真偽値を返すため、通常の失敗表示は「config.jsonの保存処理が失敗しました」となる。
6. **アプリ内の状態を更新**: `updateAppState(configData)` が Redux の更新アクションを dispatch し、対象項目を反映する。さらに `setForm(configData)` で整形済みの値を画面に反映する。
7. **データを再取得**: `await loadDataBase({ reason: 'config-saved', useAutoSwitching: false })` を実行する。
8. **結果を通知**: 再取得の成否に応じて成功またはエラートーストを表示する。
9. **保存中状態を解除**: 成功・失敗のどちらでも `finally` で `setIsSaving(false)` を実行する。再取得が終わるまで保存ボタンは無効のまま。

## 3. 保存する項目と整形ルール

定義元: `parts.js` の `DEFAULT_CONFIG_FORM` と `normalizeConfigData`（43行目）。

| 項目 | 保存時の処理 |
| --- | --- |
| `APP_LOCK_ENABLED` | 厳密に `true` の場合だけ `true`、それ以外は `false` |
| `APP_LOCK_PASSCODE` | 文字列化。前後の空白を保持 |
| `HUG_USERNAME` | 文字列化し、前後の空白を除去 |
| `HUG_PASSWORD` | 文字列化。前後の空白を保持 |
| `OPENAI_MAIL` | 文字列化し、前後の空白を除去 |
| `OPENAI_PASSWORD` | 文字列化。前後の空白を保持 |
| `GEMINI_API_KEY` | 文字列化し、前後の空白を除去 |
| `GEMINI_MODEL` | 文字列化・空白除去後、空なら `gemini-3.5-flash` |
| `DEEPSEEK_MAIL` | 文字列化し、前後の空白を除去 |
| `DEEPSEEK_PASSWORD` | 文字列化。前後の空白を保持 |
| `OPEN_ROUTER_API_KEY` | 文字列化し、前後の空白を除去 |
| `OPEN_ROUTER_MODEL` | 文字列化し、前後の空白を除去。空文字を許容 |
| `OLLAMA_URL` | 文字列化し、前後の空白を除去 |
| `OLLAMA_MODEL` | 文字列化・空白除去後、空なら `gemma4:latest` |

文字列項目は `null` / `undefined` の場合、まず空文字として扱う。パスコードは trim しないため、空白だけの入力も現在の空文字チェックを通過する。メール形式・URL形式・APIキーの有効性や、各サービスへのログイン可否を検証する処理は、この保存経路にはない。

## 4. config.json に書き込むまでの経路

```text
ConfigTab.handleSave
  → utils/config/configUtils.saveConfig(configData)
  → window.electronAPI.saveConfig(configData)
  → ipcRenderer.invoke("save-config", data)
  → main の "save-config" ハンドラー
  → fs.writeFileSync(filePath, JSON.stringify(data, null, 2), "utf8")
```

| 実装箇所 | 内容 |
| --- | --- |
| `renderer/src/utils/config/configUtils/index.js:12` | Electron APIを呼ぶ。`result.success` が偽、または例外発生時は `false`、成功時は `true` を返す。main の詳細エラーは呼び出し元に返さずログに出す |
| `electron/preload/electronApi.js:529` | `save-config` IPC を呼ぶ |
| `electron/main/parts/readfile/configHandler/index.js:94` | データがオブジェクトか確認し、ディレクトリを作成して JSON を書き込む。成功時 `{ success: true }`、失敗時 `{ success: false, error }` を返す |
| `electron/main/parts/utils/pathResolver.js:5` | 保存先を開発時・パッケージ時で切り替える |

main 側では `GEMINI_API_KEY`、`OLLAMA_URL`、`HUG_USERNAME` のキーが存在しない場合に限り、デフォルト値で補完する。空文字を拒否するチェックではなく、このフォームからは3キーとも常に渡される。

保存先:

- 開発時: リポジトリの `electron/data/config.json`
- パッケージ時: `app.getPath("userData")/data/config.json`

**既存ファイルとのマージは行わず、渡されたオブジェクトで全体を上書きする。** このボタンが渡すのは上表の14項目なので、既存ファイルにそれ以外のキーがあれば、この保存処理では保持されない。一方、Redux の更新は対象項目の部分更新であり、ファイル上書きとは動作が異なる。

## 5. 保存後のデータ再取得

実装元: `renderer/src/hooks/useDataBase/index.js:22`。

1. アプリが初期化前、またはこのフックのインスタンスで取得中かつ強制実行でない場合、取得をスキップして `false` を返す。
2. `laravelApi.getAllTables()` → `window.electronAPI.laravel_fetchTableAll({})` で Laravel のテーブルデータを取得する。
3. テーブルデータを整形し、`dispatch(fetchAllTables(tables))` で Redux の databaseSlice に反映する。`fetchAllTables` 自体は渡されたデータを受け取る thunk で、ここで再度通信するわけではない。
4. `dispatch(fetchLaravelAuthState())` により `window.electronAPI.laravel_auth_me()` を呼び、認証状態も再取得する。
5. 正常経路では `true`、テーブル取得失敗や捕捉した例外では `false` を返す。

`ConfigTab` のコメントには「現在選択中のDB/API」「AUTO_SWITCHING」とあるが、現在の `useDataBase` は Laravel 専用。`useAutoSwitching: false` は受け取っても実際の切替処理には使わず、MariaDB・SQLite への切替やフォールバックは行わない。

認証取得の thunk は `.unwrap()` せず、戻ったアクションの成否も確認していない。そのため、認証取得が rejected になっても、それだけでは `loadDataBase` が `false` を返すとは限らない。成功トーストは、認証取得まで含めた完全な成功を保証しない。

## 6. 結果ごとの表示と状態

| 状況 | 表示・結果 |
| --- | --- |
| ロック有効・パスコード空 | 「ロックをONにする場合はパスコードを入力してください」。保存しない |
| ファイル保存に失敗 | 通常は「config.jsonの保存処理が失敗しました」。Redux 更新・再取得には進まない |
| 保存成功・再取得成功 | 「Config.jsonを保存し、データを再読み込みしました」 |
| 保存成功・再取得が `false` | 「Config.jsonは保存しましたが、データの再取得に失敗しました」。保存と Redux 更新は完了済みで、元に戻さない |
| try 内のその他の例外 | `error.message`、なければ「Config.jsonの保存に失敗しました」。すでに保存済みの内容を戻す処理はない |

保存成功時に設定モーダルを閉じたり、アプリを再起動したりする処理は、このハンドラーにはない。起動時ロックの画面説明は「保存後、次回のアプリ起動から適用されます」。

## 7. 実装上の注意点

- **対象外キーの消失**: ファイル全体を14項目で上書きする。読み込み側にはデフォルト補完があるが、既存の独自値を保持する処理ではない。
- **機密値の保存・ログ出力**: この経路はパスワード、パスコード、APIキーを暗号化せず JSON に書き込む。さらに `ConfigTab` の保存前・保存完了ログと `AppStateContext` の更新ログで設定オブジェクト全体を出力している。
- **保存と再取得は別の結果**: 再取得に失敗しても保存は取り消されない。再取得は変更内容の有無にかかわらず実行される。
- **処理中の入力**: 無効化するのは保存ボタンのみで、各入力欄には `isSaving` による無効化がない。保存中に入力した内容は、保存完了後の `setForm(configData)` などで置き換わる可能性がある。
- **コメントと実装の差**: DB の選択・自動切替については、コメントよりも現在の Laravel 専用実装を基準に理解する必要がある。
